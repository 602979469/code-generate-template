## 一、分层架构

```text
┌──────────────────────────────────────────────┐
│ 1. 配置层（用户输入）                          │
│    projectStyle: monolith（microservice 占位） │
│    moduleLayout: flat | aggregated | maven-module │
└──────────────────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────┐
│ 2. 路径解析层（LayoutStrategy 策略模式）       │
│    FlatStrategy / AggregatedStrategy /        │
│    MavenModuleStrategy（注册表按 id 取实例）    │
└──────────────────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────┐
│ 3. 模板渲染层（稳定不变）                      │
│    {Class}Controller / Service / Repository…  │
│    模板不关心布局模式，只关心包路径和类名       │
└──────────────────────────────────────────────┘
```

## 二、策略接口设计（数据驱动，不含层/文件判断）

```java
public interface LayoutStrategy {
    String id();                            // "flat" | "aggregated" | "maven-module"
    String packagePrefix();                 // "" | "modules"
    boolean businessInLayer();              // flat=true，其余=false
    Path   moduleRoot(Path outputDir, String module);  // 业务层所在根目录
}
```

统一口径（`PathResolver.resolve`）：

```java
public PathSpec resolve(LayerSpec layer, String module) {
    String pkg;
    if (layer.common() || isBlank(module)) {
        // 共享层不挂业务模块；module 为空 = 路径不含模块段（flat 等价 1.0 原样）
        pkg = basePackage + "." + layer.packagePath() + "." + layer.packageSub();
    } else if (strategy.businessInLayer()) {
        // flat：业务模块作为层内子包
        pkg = basePackage + "." + layer.packagePath() + "." + module + "." + layer.packageSub();
    } else {
        // aggregated / maven-module：包路径一致，仅根目录不同
        pkg = basePackage + "." + strategy.packagePrefix() + "." + module + "."
                + layer.packagePath() + "." + layer.packageSub();
    }
    return new PathSpec(strategy.moduleRoot(outputDir, module), pkg);
}
```

## 三、策略实现类

| 策略类 | id | packagePrefix | businessInLayer | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| FlatStrategy | flat | `""` | true | 1.0 层模块不新建，业务模块为层内子包 |
| AggregatedStrategy | aggregated | `modules` | false | 业务模块子项目收在 `modules/{artifactPrefix}-{module}/` |
| MavenModuleStrategy | maven-module | `modules` | false | 业务模块子项目平铺 `{artifactPrefix}-{module}/` |

注册与路由：

- 配置 `projectStyle` + `moduleLayout` 组合为策略 id：`monolith:flat` / `monolith:aggregated` / `monolith:maven-module`；未配置 = `monolith:flat`；
- `microservice:*` 注册占位 id，配置到即抛"暂未支持"；
- 策略通过注册表（`Map<String, LayoutStrategy>`）按 id 取实例，生成流程只依赖接口，无分支判断。

## 四、插件机制（协议先行，第一版不落地具体插件）

### 4.1 配置

```yaml
plugins:
  - name: sa-token   # config 参数位预留（第一版固定模板）
```

### 4.2 插件目录协议

`templates/plugins/{name}/` 下：

- `plugin.yaml`：插件名、激活配置项、**目标文件清单**（每项 = 目标模块 + 子包 + 模板/静态内容 + 类名规则或固定文件名）、**maven 依赖**（gav + `targetPom: root | 模块名`）；
- 对应 `.ftl` / 静态文件。

### 4.3 生成行为

- 工程级、一次性：骨架初始化后生成一次，**已存在的文件跳过、不覆盖**；
- 插件文件目标 = `common-framework` / `common-util`（2.0 共享层），路径一律走统一 `resolve()`，插件自身不拼路径；
- 插件不负责表：涉及表的业务走正常 `tables:` 生成，不进入插件机制。

### 4.4 本期范围

- 只落地插件协议与路由骨架；**不迁移 sa-token 等具体插件/业务代码**；
- 迁移范围仅限：CRUD 相关代码（层目录表）与 CRUD 用到的工具类规范（common-util 的 `AssertUtil` / `LoggerUtil` / `ConvertUtil` / `ApiResult` 等使用约定）。

## 五、共享类归属（2.0 调整点）

- core-model 里的**公共类**（`BaseModel`、`ErrorCode`、`UserContext`、`BaseEnum` 等跨业务域共享的模型/接口）迁到 **common-framework**；
- core-model 只保留业务域相关的 `domain / param`（每表生成的领域模型与查询参数）；
- common-framework / common-util 是 2.0 的共享层与插件代码落点，不挂业务模块。

## 六、扩展点

| 扩展方向 | 改动位置 | 成本 |
| :--- | :--- | :--- |
| 新增一层（如 gateway） | 层目录表加一行（层 id / 子包 / 类名规则 / 模板）+ 模板文件 | 小 |
| 新增布局模式 | 新增 `LayoutStrategy` 实现类 + 注册表一行 | 小 |
| microservice（多服务/多仓） | 策略 + 骨架差异（每服务 bootstrap/pom/Dockerfile），二期 | 中 |
| 具体插件（sa-token 等） | 按 4.2 协议新增插件目录，生成器零改动 | 中 |
